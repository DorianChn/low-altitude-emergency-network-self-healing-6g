# 第二阶段报告：AI 智能调度与动态网络自愈

## 1. 范围与结论

本阶段在第一阶段工程上新增动态网络事件、无人机能耗状态、滚动时域约束搜索、三策略配对实验、逐种子 JSON、指标图表和自动化测试。第一阶段配置、CLI、基准 JSON 和规则网格策略均保留。

这是用于 AI+6G 场景研究的抽象仿真。新增调度器是确定性的滚动时域 beam search，**不是经过训练的机器学习模型**，也没有经真实 6G 设备、无线网或 3GPP 协议栈验证。

20 种子实验显示 C 策略相对 A 无无人机恢复提高连接和救援服务；与 B 第一阶段静态网格策略相比，C 的能耗和条件平均时延略低、连接率接近，但救援服务率低 3.31 个百分点、平均恢复时间晚 50 秒、P95 略高，且算法计算成本明显更大。因此第二阶段的动态功能和算法接口已交付，但实验没有证明 C 已全面优于第一阶段；第三阶段若以竞赛性能提升为目标，应先改善救援部署选址和恢复速度。

## 2. 实现模块

- `dynamic_config.py`：独立动态 TOML 模式和校验；第一阶段场景配置不需要迁移。
- `dynamic_world.py`：每个种子预生成基站/业务事件和用户移动轨迹，三种策略共享同一轨迹；保存事件时间戳、位置帧摘要及世界轨迹 SHA-256。
- `dynamic_simulation.py`：离散时间事件推进、基站故障与恢复、流量倍率、回传中断、用户随机游走、无人机位置/电池更新、三组控制器及指标采样。
- `optimizer.py`：网络诊断和在线有限时域 beam search；候选动作是保持、八方向移动和朝可行救援用户—基站回传区域移动。每次只执行首个动作。
- `experiment.py`：至少 20 个固定种子的统一实验、跨种子均值/样本标准差、按配对世界轨迹计算的非时延差值，以及未恢复场景的明确统计口径。
- `charts.py`：依据实际 JSON 汇总和逐样本时延生成指标总览及条件时延分布 PNG/SVG 图。
- CLI 新增 `run-dynamic`；原 `run` 命令保持兼容。

## 3. 优化算法

### 3.1 状态诊断和重规划

每个仿真时刻评估网络并识别：故障基站、未连接用户、无覆盖用户、受容量阻塞用户、未连接救援用户、利用率达到拥塞阈值的资源及无人机回传状态。

调度器对网络状态签名进行比较。站点健康、回传状态、失联用户、拥塞资源、用户位置/需求或资源利用率变化时触发重新规划；状态不变时，在配置的周期到期后重新规划。当前动态基准中，C 每次运行作出 61 次决策（第一次决策 + 60 次重规划）。不可行决策写明原因，例如 `no_healthy_base_station`、`drone_backhaul_temporarily_unavailable`、电池储备或返航能量不足、候选点超出城市边界/回传范围。

### 3.2 目标函数

对长度为 (H=3) 的候选动作序列最大化各预测步收益之和：

```text
J = Σ[k=0..H-1] (
      w_r · R_k/N_r
    + w_c · C_k/N
    + w_b · 1[所有救援用户均连接]
    - w_l · min(L_k/200 ms, 1)
    - w_e · E_k/600 Wh
    + w_p · clip((d_k - d_(k+1))/(v·Δt), -1, 1)
)
```

其中 (R_k) 是成功连接救援用户数，(C_k) 是全部连接用户数，(N_r) 和 (N) 是相应用户总数，(L_k) 是当前候选网络的成功连接用户平均时延，(E_k) 是移动、悬停和实际中继用能，(d_k) 是无人机到最近可行救援用户—基站中继位置的距离。配置权重为 `w_r=10`、`w_c=3`、`w_b=2`、`w_l=1.5`、`w_e=2`、`w_p=4`。同一序列每步累计，未设置折扣因子。网络引擎按救援优先级和容量约束计算 (R_k,C_k,L_k)，不把预期连接结果写成固定值。

### 3.3 动作和硬约束

beam width 为 6。每个搜索节点展开保持、八个罗盘方向和朝可行中继位置的单位方向动作，按网络引擎重新评估覆盖、用户业务分配、基站/无人机容量和时延。搜索到的完整序列只执行第一个 10 秒动作，然后根据新观测重新规划；第一阶段 B 则只在起始时刻作一次完整规则网格搜索。

每个候选动作须满足：

- 城市边界：(0 ≤ x ≤ 10) km，(0 ≤ y ≤ 10) km。
- 单步飞行距离：(|x_{k+1}-x_k| ≤ vΔt)，当前配置最大 0.15 km/10 秒。
- 接入、回传距离和链路容量由公共网络引擎检查；无人机回传断开或不存在健康基站时不构造可用中继链路。
- 可用电量 (B_{k+1} ≥ B_{reserve})，且按最近健康基站估算返航移动能耗后仍保留 (B_{reserve})。默认初始电池 600 Wh、储备 50 Wh、移动能耗 18 Wh/km、悬停功率 80 W、中继功率 120 W。

当前返航储备只估算返航飞行能耗，没有计入返航途中的悬停、中继用能、风场或电池老化；详见限制部分。

## 4. 实验配置与统计口径

- 配置：`configs/dynamic_scenario.toml`，基础网络引用第一阶段 `configs/disaster_scenario.toml`。
- 随机种子：2026–2045，共 20 个。每个种子预先生成同一份用户随机游走轨迹和事件轨迹，A/B/C 均复用；随机轨迹 SHA-256 保存在 JSON。
- 时域：600 秒，10 秒步长，共 61 个采样时刻；城市 10 km × 10 km；40 用户，其中 8 名救援用户。
- 事件共 12 个：第 60 秒 bs-west 故障、第 180 秒恢复；第 230/300 秒将业务倍率调整到 1.30/1.00；第 330/370 秒无人机回传中断/恢复；第 400/450 秒 bs-west 再次故障/恢复；第 460/500 秒业务倍率变为 1.35/1.00；第 520/570 秒恢复 bs-central/bs-east。
- 用户每 10 秒以独立均匀随机位移更新，单坐标变化不超过 0.025 km；仿真事件、移动更新、策略决策和无人机能耗变化均带时间戳。
- A 为无无人机恢复措施，但地面站仍按统一事件恢复；B 为第一阶段静态网格策略；C 为本报告滚动时域调度器。
- 连接率/覆盖率/救援服务率按全时域用户—时刻机会数求比例；恢复时间是首次同时服务全部救援用户的离散采样时刻；未恢复记 `null`，只用已恢复运行计算恢复时间均值。
- 时延只对各自策略成功连接的用户—时刻样本统计。表中 pooled 平均值和 pooled P95 是跨种子的成功样本池统计；不同策略的成功样本集合不同，因此不计算配对时延差。
- 连接、救援服务、覆盖、能耗和计算耗时按每个种子一个值汇总，给出等权跨种子均值和样本标准差。算法计算时间是运行时墙钟测量，和仿真恢复时间分开。

## 5. 实际对照结果

下表是 [`results/phase2_20_seed_results.json`](../../results/phase2_20_seed_results.json) 的实际汇总。比例显示为均值 ± 跨种子样本标准差；时延为 pooled 成功连接样本统计；恢复时间为恢复运行均值。

| 指标 | A 无无人机恢复 | B 静态网格 | C 滚动优化 |
|---|---:|---:|---:|
| 覆盖率 | 18.547% ± 4.205% | 25.836% ± 4.031% | 25.451% ± 3.989% |
| 用户连接成功率 | 18.525% ± 4.199% | 24.760% ± 3.639% | 24.738% ± 3.748% |
| 救援用户服务成功率 | 14.754% ± 0.000% | 28.504% ± 1.379% | 25.195% ± 1.223% |
| 恢复成功/未恢复 | 20/20 / 0/20 | 20/20 / 0/20 | 20/20 / 0/20 |
| 已恢复运行平均恢复时间 | 520.0 s | 450.0 ± 49.7 s | 500.0 s |
| pooled 平均通信时延 | 31.284 ms | 49.940 ms | 46.610 ms |
| pooled P95 通信时延 | 66.524 ms | 129.035 ms | 129.182 ms |
| 无人机能耗 | 0 Wh | 130.139 ± 10.859 Wh | 125.967 ± 1.529 Wh |
| 算法决策总耗时/600 秒运行 | 0 ms | 127.424 ± 10.782 ms | 1,429.905 ± 122.540 ms |
| C 的平均单次决策耗时 | — | — | 23.441 ± 2.009 ms |

20 组匹配种子中，C 的救援服务率有 19 组低于 B、1 组持平，没有高于 B；`C-B` 救援服务率差均值为 `-0.033094`，恢复时间差（两者均恢复的配对种子）为 `+50.0 s`。C 相对 B 的用户连接率差均值为 `-0.000225`，平均无人机能耗差为 `-4.172 Wh`。C 的 pooled 平均时延比 B 低约 `3.330 ms`，pooled P95 比 B 高约 `0.146 ms`；时延样本集合不同，不进行用户级配对或因果推断。

本实验支持的结论是：C 以更高决策计算成本换取少量平均时延和能耗改善，整体连接率接近 B，但没有达到 B 的救援服务率和恢复速度。它相较 A 有改善，但尚不能取代 B 作为当前核心救援性能策略。

## 6. 失败与不可行案例

- 20 个种子均恢复成功，主要因为事件表安排了健康地面站恢复；本组实验没有观测到 `network_recovery_time_s=null` 的完整 600 秒运行。未恢复统计逻辑另由 60 秒截断场景测试：三个策略均保留 `null`，恢复计数为 0，成功运行时间均值为 null。
- C 平均每次运行有 21 次明确不可行的重规划：17 次因“没有健康基站”，4 次因“无人机回传暂时不可用”。此时禁止使用无人机中继，调度器输出原因并等待下一次状态变化。
- C 每个种子执行 61 次决策（初次决策 1 次，之后 60 次重规划）；墙钟计算总时间均值约 1.43 秒/完整模拟运行。原因之一是用户位置每 10 秒变化，触发滚动重规划，并且 beam 会计算多个网络候选快照。
- 当前高能耗和较差恢复时延揭示了目标生成/服务中心选址不足：C 仍会追逐最近可行救援中继点，缺少更强的多用户聚类覆盖和较远期移动预测。对同一批种子重复调权并挑最好结果不构成独立验证，本阶段没有这样做。

## 8. 复现步骤和产物

```bash
uv sync --extra dev
uv run lowalt6g run-dynamic \
  --config configs/dynamic_scenario.toml \
  --output results/phase2_20_seed_results.json \
  --plots plots
uv run pytest -q
```

逐种子事件和网络指标在 JSON 中；4 张图（指标总览 PNG/SVG、条件时延分布 PNG/SVG）位于 `plots/`。算法耗时受本机硬件和系统负载影响，因此即使其他动态网络指标可重现，完整 JSON 的耗时字段仍可能变化。

## 9. 技术限制和后续门槛

- 二维欧氏距离，无海拔、三维飞行、天线方向图、建筑遮挡、多径、干扰、频谱或协议栈。
- 未实现 3GPP 信道、真实 RAN/核心网、无人机通信设备联调、现场测量或参数校准。
- 用户用独立随机游走表示，不含道路网络、群体协同、救援队轨迹或真实移动速度校准；业务仅用全网倍率缩放。
- beam 搜索预测步冻结当前用户位置、业务量和基站状态；没有未来事件预测、随机移动预测、滚动充电、能耗不确定性或风险敏感目标。
- 电池模型是功率/能耗预算抽象，不含电池非线性、环境温度、风阻、飞控功耗和返航路径几何细节。
- 当前配置权重未通过消融实验、置信区间分析或外部网络数据校准；20 个种子可用于基础复现，不能代表所有灾害场景。
- 第三阶段若要宣称“智能调度优于规则基线”，至少应改进救援服务率/恢复时间，控制决策耗时，并在未参与调参的种子或不同故障/负载配置上复核。

**阶段判断：**工程功能和自动化验证达到第二阶段交付要求；竞赛性能验证未达到“滚动策略优于第一阶段”的门槛。建议第三阶段先围绕救援用户组覆盖选址、有限时域终端价值估计和计算预算迭代，再扩展演示前端；当前结果不能作为获奖或真实 6G 性能依据。
